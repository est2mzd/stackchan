# StackChan 実装計画

- 入力: `user_directions/001_objective.md`
- 作成日: 2026-09-08
- 前提: 公式スマホアプリ（StackChan World）は使わない。StackChan は入出力端末、PC または Jetson が頭脳。

## 1. 結論（いま決めること）

やりたいことは3つある。会話、時計モード、カレンダー通知。いずれも **マイク / 画面 / スピーカーを PC 側から制御できること** が共通前提になる。

出荷時ファームはスマホアプリ前提なので、アプリ連携を直しても目的には届かない。参考記事の「ペアリングできない」問題は、公式アプリ経路の詰みであり、本計画では追わない。

採用する構成は次のとおり。公式スマホアプリと公式クラウドは登場しない。

```
+---------------------------+     Wi-Fi（主）      +---------------------------+
| PC（のち Jetson）         |     USB（予備）      | StackChan                 |
|                           |                      |                           |
|  中でやること             |  <--- マイクの音     |  中でやること             |
|    音声を文字にする       |                      |    マイクで録る           |
|    意図を分ける           |  ---> 返事の音声     |    スピーカーで鳴らす     |
|      「会話」→ LLM        |  ---> 画面の文字     |    液晶に出す             |
|      「時計モード」→ 日時 |                      |      日付                 |
|      予定が近い → 読み上げ|                      |      時刻                 |
|    カレンダーを見る       |                      |      曜日                 |
|                           |                      |      （会話時は字幕）     |
+---------------------------+                      +---------------------------+

LLM は PC の中だけ。StackChan の中では動かない。
```

- 本体は ESP32-S3（CoreS3）なので、LLM は載せない。音声認識・生成・予定管理はホスト側。
- 最初のホストは作業中の Linux PC。Jetson は同じ HTTP/WebSocket インタフェースを保てば後から載せ替え可能。
- 接続は Wi-Fi を主、USB はフラッシュとデバッグ用。有線運用は予備。

## 2. 目的の分解

| # | やりたいこと | 入力 | 処理 | 出力 | 依存 |
|---|---|---|---|---|---|
| 1 | 会話 | 本体マイク | ホスト上の Local LLM または ChatGPT | スピーカー + 画面文字 | 音声往復とホスト接続 |
| 2 | 時計モード | 「時計モード」という音声 | ホストまたは本体で日時文字列生成 | 画面に日付・時刻・曜日 | 音声コマンドと画面描画 |
| 3 | 予定通知 | PC 上の Google Calendar 連携 | ホストが X 分前に文言作成 | 画面（時計 + 予定）と音声読み上げ | 時計表示 + Calendar API + TTS |

実装順は依存の薄い順にする。

1. 接続と画面表示
2. 時計モード（タッチまたは仮コマンドでも可）
3. マイク入力と音声コマンド
4. 会話
5. Google Calendar 通知

時計を先にすると、接続・画面・時刻同期を会話より先に検証できる。カレンダーは時計画面の上に載せる。

## 3. 現状認識

- 2026-08 頃に購入。公式完成品（SKU: K151 想定、CoreS3 + サーボ本体）。
- スマホアプリとはうまく連携できていないが、本計画ではアプリは使わない。
- 参考記事（[zenn.dev/shogaku/articles/stackchan-pairing-firmware](https://zenn.dev/shogaku/articles/stackchan-pairing-firmware)）が示す事実:
  - 出荷ファームが古いとアプリの検証で落ちる（画面上は `No devices found`）。
  - 新しい公式ファームは OTA 依存、OTA は Wi-Fi、Wi-Fi はアプリ、アプリは新ファーム、という循環。
  - 公式アプリを通すには USB で公式バイナリを書く必要がある。公開ソースのハンドシェイクはスタブ。
- 公式ファームを最新にしても、会話先は公式クラウド / アプリ側エージェントになる。Local LLM・時計モード・Google Calendar は公式ファームの守備範囲外。
- CoreS3 制約:
  - マイクとスピーカーは同時使用できない。発話中は録音停止が必要。
  - USB-C は CoreS3 側とかかと側の2つ。同時給電しない。書き込み・給電はかかと側推奨。
  - PC の USB 給電では充電が足りないことが多い。運用は USB 充電器。
  - シリアルポートを開くと本体が再起動する。ログ取得と操作は同時にできない。

## 4. アーキテクチャ

### 4.1 役割分担

**StackChan（ファーム）**

- Wi-Fi 接続とホストへのセッション維持
- マイク録音 → PCM/Opus をホストへ送る
- ホストからの音声を再生
- ホストからの画面指令（時計、字幕、予定）を描画
- ウェイク（タッチ、または簡易ウェイクワード）で会話セッション開始
- サーボは後回し。顔と首振りは任意

**ホスト（Python）**

- ASR（faster-whisper / FunASR などローカル、またはクラウド STT）
- 意図ルーティング
  - 「時計モード」→ 時計画面へ切替
  - 「会話」/ 通常発話 → LLM
  - システム内部イベント → 予定読み上げ
- LLM（Ollama / LM Studio / ChatGPT API を設定で切替）
- TTS（ローカル Piper / OpenJTalk、またはクラウド TTS）
- Google Calendar ポーリングと通知スケジューラ
- 時計用 NTP / ホスト時刻の配信

### 4.2 通信

主経路は LAN 上の WebSocket。

```
ws://<PC_IP>:8000/stackchan
```

メッセージ例（実装時に正式スキーマ化する）:

- `audio_in` / `audio_out`: 音声フレーム
- `transcript`: 認識テキスト（画面字幕用）
- `display`: `{mode: clock|chat|alert, lines: [...]}`
- `event`: `{type: calendar_soon, title, start_at}`
- `mode`: `{name: clock|chat}`

予備経路は USB シリアル。Wi-Fi が不安定なときのデバッグと、初期フラッシュ専用。常時有線会話は帯域と再起動制約があるため主経路にしない。

### 4.3 ファームの選び方

自前でゼロから書く前に、既存実装を評価してから決める。

| 候補 | 向いている点 | 懸念 |
|---|---|---|
| コミュニティ stack-chan（Moddable / JS MOD） | 顔・サーボ・TTS 連携の資産が多い | ホスト分割が本計画と一致しない場合がある |
| Arduino / ESP-IDF 自作（M5Unified） | 画面・マイク・スピーカーを直接制御できる | 音声ストリーミングとセッション管理を自前実装する |
| 既存の「本体=I/O、PC=頭脳」系（例: websocket-control-stackchan, xiaozhi 系ローカルエージェント） | 目的の役割分担に近い | プロトコル追従、日本語、公式 K151 対応の確認が必要 |

推奨: **フェーズ 0 で上記を実機評価し、K151 でマイク・スピーカー・画面が動くものを土台にする。** 動かない場合は Arduino + M5Unified で最小ファームを自作する。公式ファームはロールバック用にバイナリを保存してから上書きする。

## 5. フェーズ計画

### フェーズ 0 — 現状把握と土台選定（最初にやること）

完了条件:

- 本体の SKU、シリアル起動ログのファーム版数、USB ポート認識を記録する
- 公式最新ファームのバイナリを保存する（戻せる状態）
- Linux PC から `esptool` でフラッシュできることを確認する
- 土台ファームを1つ選ぶ

作業:

1. かかと側 USB-C のみ接続し、`lsusb` / `esptool flash-id` で ESP32-S3 と 16MB フラッシュを確認する
2. 起動ログから現行 `App version` を取る（ポートオープンで再起動することを承知する）
3. M5Burner API から `StackChan-UserDemo` の現行版を保存する
4. 候補ファームを1つ焼き、画面表示と Wi-Fi 接続まで確認する

このフェーズではアプリペアリングを目標にしない。

### フェーズ 1 — ホスト接続と時計表示

目的 2 の画面部分だけ先に通す。マイクはまだ必須ではない。

完了条件:

- 本体が PC の WebSocket に接続する
- ホストが 1 秒ごとに日時を送り、画面に次の形式で出す

```
2026/09/08
22:58:33
Tuesday
```

- 表示言語は設定で日本語曜日にも切替可能にする（初期は指定どおり英語曜日でよい）
- 切断時は本体側に「未接続」と出す

ホスト側は最小の Python サーバでよい。LLM は入れない。

### フェーズ 2 — 音声コマンドで時計モード

完了条件:

- 本体マイクの音声がホストに届く
- ASR が「時計モード」を認識したら時計画面に入る
- 復帰コマンド（例: 「会話モード」「戻って」）で時計を抜ける
- マイク/スピーカー排他を守り、再生中は録音しない
- タッチでも同じモード切替ができる（ASR 失敗時の逃げ道）

ASR 初期実装は faster-whisper small/medium、日本語。ウェイクワード専用モデルは後回し。誤検出はコマンド語句を短く固定して抑える。

### フェーズ 3 — 会話

完了条件:

- タッチまたは発話開始でセッション開始
- マイク → ASR → LLM → TTS → スピーカー
- 画面にユーザ発話と応答テキストを出す
- LLM は設定で切替
  - ローカル: Ollama など OpenAI 互換
  - クラウド: ChatGPT API
- 会話中に「時計モード」と言えばフェーズ 2 に遷移する

注意:

- 本体では LLM を動かさない
- 応答待ち中は顔または「考え中」表示
- タイムアウトと切断復帰を入れる

### フェーズ 4 — Google Calendar 通知

完了条件:

- ホストが Google Calendar API（OAuth）で予定を取得する
- 設定した X 分前（初期 10 分、設定変更可）に通知する
- 画面は時計表示を維持したまま予定タイトルを追加する
- 同時に TTS で読み上げる（例: 「10分後、定例ミーティングです」）
- 本体電源オフ中に過ぎた通知は、再接続時に「過ぎた予定」として一度だけ出すか、捨てるかを設定する（初期は捨てる）

Calendar は本体に持たせない。トークンはホストのローカルファイルに置き、リポジトリに含めない。

### フェーズ 5 — Jetson 載せ替えと仕上げ（任意）

完了条件:

- ホストのインタフェースを変えずに Jetson で同じサーバを起動できる
- README にフラッシュ、Wi-Fi、ホスト起動、Calendar OAuth、LLM 切替を書く
- 公式ファームへの戻し方を書く

## 7. リスクと回避

| リスク | 影響 | 回避 |
|---|---|---|
| 公式ファームにロックされ、カスタムが書き込めない | 全停止 | フェーズ 0 で esptool 書き込みを先に確認する。公式 bin を保存する |
| 候補ファームが K151 サーボ/タッチ非対応 | 首振りやタッチが使えない | 画面・音・通信を優先。サーボは後回し |
| マイクとスピーカーの同時使用 | ハウリング、録音失敗 | 発話中は Mic.end / Speaker.begin を切り替える |
| 2.4GHz Wi-Fi の不安定 | 音声途切れ | 同一 AP、固定 IP、再接続、USB デバッグ経路 |
| ASR が「時計モード」を取りこぼす | モードに入れない | タッチ代替、画面ボタン、短い定型句 |
| Calendar OAuth とトークン管理 | 通知が動かない、秘密情報漏洩 | ホストローカルのみ。`.gitignore` |
| PC USB 給電不足 | サーボ不定、充電しない | 運用は充電器。開発時も給電に注意 |
| 日本語フォント不足 | 画面が □ になる | フェーズ 1 で日本語フォントを載せるか、時計は英数字のみ先に通す |

## 8. 最初の実装タスク（次レポート以降で着手）

1. 実機の版数・USB 認識・給電ポートを記録する
2. 公式ファーム bin を `firmware/official/` に保存する（git 管理するかはサイズ次第。LFS またはローカルのみ）
3. 土台ファームを1つ選んでフラッシュし、画面 Hello World を出す
4. ホスト Python で WebSocket を開き、時計文字列を 1Hz で送る
5. 本体で時計描画を実装する

ここまでがフェーズ 1。これが通れば目的 2 の半分は完了し、目的 1 と 3 の土台になる。

## 9. 非目標（やらないこと）

- StackChan World アプリとのペアリング復旧を本線にしない
- 公式クラウド AI エージェントへの依存
- 初回から Jetson 必須にしない
- 初回からサーボダンス、カメラ顔認識、NFC を入れない
- 本体単体での LLM 推論

## 10. 成功条件（ユーザ要求との対応）

1. **会話**: 本体マイクで話し、PC/Jetson の Local LLM または ChatGPT が答え、本体スピーカーと画面文字で返る。接続は無線（主）または有線（予備）。
2. **時計モード**: 「時計モード」で画面が `YYYY/MM/DD` / `HH:MM:SS` / `Weekday` になる。
3. **予定通知**: PC 上の Calendar 連携が X 分前に画面表示と音声読み上げを行う。時計表示と共存する。
